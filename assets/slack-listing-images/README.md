# Slack Marketplace listing images

1600×1000 PNGs for the Bratrax listing. Each one is a **real Slack screenshot**
on a Bratrax-branded plate — only the identity is edited.

Filenames are the upload order. Slack's reviewers study the first image
hardest, so `01` leads with the densest single frame: a real ranked table, the
explanation above it, and the full button row.

| File | Headline | Shows |
|---|---|---|
| `01-campaign-table.png` | The whole table, in the **thread** | A ranked ROAS table with the model's read of it, plus the deep link and the 7/30/90-day re-runs |
| `02-channel-trend.png` | See every channel at **once** | Five channels over 14 days as a native Slack chart |
| `03-follow-up.png` | Ask the obvious **follow-up** | Two exchanges in one thread, the second scoped off the first |
| `04-suggested-prompts.png` | Know what to ask on **day one** | The Messages tab on first open, with the three suggested prompts |
| `05-revenue-chart.png` | See what actually drove **revenue** | Revenue by channel as bars. A spare — `02` covers charts better |

Slack allows six. Four is a strong set; `05` overlaps `02` and sits smallest,
so use it only to fill the gallery.

## `email-connect-slack.png` is not a listing image

It shows the Bratrax web app, not Slack. Slack's image guidance is explicit —
*"show your app/service in the context of Slack, not other tools your service
may integrate with"* — and a submission can be returned over it. It is built
here for the **customer email**, where pointing people at Settings → Slack is
the entire job.

## Why real captures, not rebuilt ones

The first attempt redrew the Slack cards in HTML, following Slack's own example
listing image (their Helpdesk card is a redraw, not a capture, deliberately
zoomed so it survives the gallery thumbnail). That was the wrong call here. A
reconstruction that is 95% right — slightly wrong button radius, slightly wrong
badge weight — reads as suspicious to a reviewer holding the listing next to the
live app. A real capture cannot. Legibility is the price, and it is worth
paying.

## Regenerating

```bash
python3 patch.py     # originals/ -> shots/ : photo -> initial tile, name -> "Julia"
python3 make.py      # shots/ + branded plate -> the finished 1600x1000 PNGs
```

Needs Pillow and a Chromium build; the Chromium path is a constant at the top
of `make.py`.

- `originals/` — the untouched captures. Never edit these.
- `shots/` — generated by `patch.py`. Never edit by hand; they are overwritten.
- `fonts/` — Lato and Outfit, vendored because the patch has to match Slack's
  UI face and the Bratrax app's respectively.

Headlines live in the `IMAGES` list in `make.py`; the plate styling is the
`PLATE` template in the same file.

## What `patch.py` changes, and what it deliberately does not

Only identity: the profile photo becomes a plain initial tile, and
"Yuliya from Bratrax" becomes "Julia". In the Bratrax settings capture, which
has no Slack chrome at all, it is just the account chip in the header — located
by its fill colour rather than by luminance, and redrawn in Outfit because that
is the app's own face. Every number, timestamp, button and pixel of UI is the
original capture.

Two details make the name swap invisible rather than obviously pasted:

- **Real Lato.** Slack's UI face is Lato, so the replacement is drawn in it
  rather than a lookalike.
- **The point size is solved, not guessed.** The captures were taken at
  different UI scales (16px and 20px across the set). `patch.py` re-renders the
  *original* string and binary-searches the size until its width matches the
  pixels being replaced.

"Julia" is far shorter than "Yuliya from Bratrax", so the adjacent timestamp is
erased and redrawn too. Leaving it in place would open a gap that never occurs
in Slack — exactly the kind of tell that reads as doctored.

The avatar threshold is 235, not something closer to white: the photo's rounded
corners are antialiased, and a looser threshold swallows that halo into the
bounding box and oversizes the replacement tile.

## Known trade-off on the chart images

`02` and `05` are the two captures that do not fill the frame: at 1050×815 and
1100×800 they are taller than the required 8:5, so they scale to 927px and
962px wide against the 1320px the others reach. Their content bounds are
already tight, so cropping buys nothing.

If either needs to be more legible, retake the thread in a **wider, shorter**
browser window: the answer text reflows to fewer lines, the thread gets wider
and shorter, and it fills the 8:5 frame at a larger scale. Drop the new capture
over the matching file in `originals/` and re-run both scripts — the header
hints in `patch.py` will need re-measuring against the new UI scale, since they
are per-capture.

## The render trap

Headless Chromium's `--window-size=W,H` sizes the *window*: the page gets a
viewport 87px shorter while the screenshot is still H tall, padded out with the
body background. The graph paper and vignette are `position: fixed`, so they
cover only the viewport and leave a band with no grid across the bottom.
`make.py` compensates the window height so the viewport lands at exactly 1000,
then crops back with Pillow. If Chromium is upgraded, re-measure that offset —
the script fails loudly rather than silently shipping a seam.
